# План перестройки архитектуры приложения

## Цель

Сделать визуальный редактор главным приложением, а публикацию, настройки и вспомогательные окна — управляемыми из него. Убрать повторный запуск EXE, скрытое главное окно Tkinter и межпроцессный обмен через временные JSON-файлы. Сохранять пользовательское поведение и выполнять изменения небольшими независимыми PR.

## Последовательность

1. **Зафиксировать текущее поведение и протокол обмена.** Добавить автоматические проверки существующего обмена между редактором и управляющей частью. Это защитная основа для следующих изменений; пользовательское поведение пока не меняется.
2. **Выделить прикладной контроллер публикации.** Перенести состояние и сценарии публикации из класса окна в отдельный компонент без привязки к Tkinter. Сохранить текущий интерфейс запуска на этом этапе.
3. **Подключить контроллер к API визуального редактора.** Перенести выбор профиля, подтверждение публикации, состояние очереди и повторную отправку в редактор. Финальная ручная правка не нужна: пользователь проверяет внешний вид публикации в самом редакторе. В каждом PR переносить ограниченный набор функций и сохранять совместимость.
4. **Сделать визуальный редактор точкой входа.** Выполнено: приложение запускает редактор напрямую, без повторного запуска EXE.
5. **Удалить устаревшую инфраструктуру.** Выполнено: удалены окно Tkinter, запуск редактора дочерним процессом и обмен публикацией/статусами через временные JSON-файлы. Редактор работает через собственный API. Следующий этап — проверить конфигурацию упаковки и жизненный цикл приложения, затем провести тесты и проверку сборки.
6. **Проверить сборку и жизненный цикл.** Запустить доступные автоматические тесты и статические проверки; отдельно проверить на Windows собранный EXE, открытие и закрытие редактора, настройки, публикацию, ошибки сети, частичную отправку и повторную отправку. Не считать сборку проверенной без фактического запуска.

## Правила безопасного перехода

- Каждый этап — отдельный PR от актуального `main`; следующий этап начинается после мержа предыдущего.
- Не менять формат профилей, черновиков и пользовательских данных без необходимости.
- Не переносить сразу весь код интерфейса: сначала выделять логику и фиксировать её поведение тестами.
- Сохранять обработку ошибок Telegram, подтверждение публикации, очередь неопубликованных сообщений и поддержку альбомов. После подтверждённого ограничения частоты Telegram визуальный редактор должен предлагать повторную отправку только оставшихся сообщений с учётом паузы. Итоговый вид проверяется в визуальном редакторе; отдельная ручная правка сформированного текста не используется.
- Старое окно Tkinter и протокол временных JSON-файлов удаляются только после переноса публикации, очереди повтора, профилей и вспомогательных действий в API редактора.
- Не заявлять об успешной сборке EXE, пока она не выполнена и не проверена на Windows.
